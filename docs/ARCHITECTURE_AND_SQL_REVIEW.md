# Architecture and SQL review — 2026-10-02

LifeLink uses Supabase Postgres as the authoritative database, RLS for per-user access, Edge Functions for server-only credentials, and Isar as a device-local offline cache/outbox. Isar is a useful cache for reception and lab work when connectivity drops. It is not a second authority: the server validates roles, ownership, and clinical write payloads before accepting changes. Sync preserves pending writes and does not overwrite them with cloud rows.

The live public tables are tiny (the largest was 112 KB at review). Visits have indexes on `(user_id, created_at)` and queue status/date; lab results have a unique `visit_id` index; guardianships have donor/status and patient indexes. Sharding or table partitioning would add cross-shard authorization, migration, and backup complexity without a measured performance benefit. Reassess only when real row counts, query plans, and maintenance needs show an issue.

The cache previously pulled a complete RLS-visible snapshot every 30 seconds. It now refreshes on sign-in/auth change, connectivity return, explicit sync, app resume, and every five minutes while foregrounded. A signed-out or expired session removes all synced clinical snapshots and profiles from Isar while keeping account-owned pending work for later recovery. Reads still use the local cache immediately. The current full-snapshot reconciliation remains suitable only for small deployments; large-scale deployment should use a server-designed incremental feed or per-role pagination with a stable snapshot cursor and deletion markers.

SQL injection review: Dart uses Supabase PostgREST filters and typed RPC parameters, with no client-built SQL statements. The only composed PostgREST expression is reception search; it now rejects every character that can change its filter grammar and limits the query to 80 characters. The sync transport also allows only three fixed table names and two fixed RPC names. Stored procedures cast UUIDs/numbers, validate enums and JSON schemas, and use no user-derived `EXECUTE`. Migration-time dynamic SQL uses identifiers/signatures read from PostgreSQL catalogs, not user input. Every public clinical table has RLS enabled; only nonclinical `app_settings` is anonymously readable. These are tested in `test/input_validation_test.dart` and the rollback-only SQL security suites.

Remaining production concern: Isar Community 3.3.2 does not expose database-file encryption in the API used here. The cache and unsynced clinical outbox are therefore protected by device access controls and operating-system storage, not app-level encryption. Do not use real patient records on shared/unmanaged devices until encrypted local storage and key recovery have been designed and tested. Also, offline data cannot reflect server-side revocation until the device reconnects; use device management and limit offline access for a real clinic rollout.
