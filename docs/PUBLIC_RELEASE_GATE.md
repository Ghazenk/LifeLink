# LifeLink release gate for real patient records

Status: **NOT APPROVED FOR PUBLIC CLINICAL USE** (2 October 2026). Use synthetic data only. A passing build, test suite, or security scan does not change this status.

The operator has confirmed that the intended release will hold real patient records and that reception and laboratory staff must run the blood bank both online and during an internet outage, then reconcile on reconnect. The current implementation does **not** meet that end-to-end requirement. These blockers are mandatory, not optional hardening:

The recommended target is a [single clinic LAN server with outbound cloud synchronization](CLINIC_LAN_ARCHITECTURE.md), so staff continue to share tokens, results and inventory while the internet is unavailable. The linked design is a proposal and has not been implemented.

| Gate | Evidence in this repository | Required acceptance evidence |
| --- | --- | --- |
| Encrypted offline records and outbox | `LocalDatabase.initialize` opens `lifelink_db` with Isar in application documents. No database encryption key is passed or supported by this Isar integration. `SyncEngine` persists profiles, visits, lab results, and pending clinical writes. | Migrate to a maintained, authenticated encrypted database; keep keys in platform keystore/keychain; test lock/unlock, power loss, account switch, lost device, key rotation, migration from existing Isar data, and recovery of unsynced writes on each supported platform. Do not silently delete pending clinical work. |
| Offline revocation and device control | An offline device cannot receive account revocation or updated RLS. Sign-out clears synced cache but intentionally preserves pending work. | Approved clinic devices with full-disk encryption, screen lock, MDM/remote wipe, per-staff accounts, bounded offline duration, device-loss process, and a tested reconciliation/conflict policy. Document who may access pending records after staff departure. |
| End-to-end offline blood-bank operation | `ReceptionRepository.issueToken` and `LabRepository.completeLabProcessing` write to a local outbox. But reception patient search, approvals, and inventory read Supabase directly; stock adjustment calls a server RPC. Lab's queue is filtered to its **own account's** cached visits. A reception visit created on another account/device during an outage cannot reach lab until connectivity returns. The app-side session gate also expires idle sessions, so it cannot be relied on for a prolonged disconnected shift. | Design a facility-scoped offline identity and encrypted data model. Preload the authorized patient directory and current stock ledger with timestamps; support offline reception-to-lab handoff over an authenticated local network or a clearly documented manual workflow; use stable operation IDs, stock reservations/allocations, duplicate prevention, conflict review, and staff audit history. Test two devices, two staff accounts, a long outage, restart, clock skew, simultaneous stock changes, revoked staff, and reconnect. Never display stale stock as guaranteed available. |
| Pediatric patient identity | `profiles.id` is an `auth.users.id`; `visits.user_id` and `guardianships.patient_id` reference profiles. Signup rejects under-13 accounts. Caregiver record sharing does not establish legal authority. | Introduce a non-login patient/clinical-subject entity and verified parent/legal-guardian relationship with recorded authority and consent basis. Update all RLS, RPCs, reception/lab flows, guardian sharing, and offline sync. Test child creation, withdrawal/revocation, adult transition, and access by unrelated users. Never create fictitious child email/password accounts or assert a false age. |
| Clinical governance | The app is an FYP, AI meal drafts are general adult suggestions, and fixed transfusion/donation date estimates were removed. | Named licensed clinical operator in Pakistan; clinical safety review, approved workflows and content, escalation and correction process, staff training, and review of applicable blood/health requirements. The doctor-review warning does not establish clinical safety. |
| Operator privacy and law | Legal pages have admin-editable operator fields; defaults are placeholders. Supabase region is Mumbai. | Enter real legal entity/facility, jurisdiction, monitored privacy and copyright contacts, retention and deletion practices, actual SMTP processor, cross-border assessment, contracts, incident procedure, and locally qualified legal review. Publish finalized pages before collecting real records. |
| Authentication and deployment | Supabase advisor still reports leaked-password protection disabled. Android release rejects the example application ID and absent private signing key. Recovery's hosted template uses an email code, but final inbox/device acceptance remains open. | Enable available breached-password checks and server session controls; verify signup confirmation and recovery on real devices; rotate credentials previously pasted into chat; establish production domain/deep links, private keystore, platform identifiers, HTTPS hosting, monitoring, backup and restore drills. Run supported-platform release builds and device testing. |
| API and database scale | RLS and role checks are present, but sync fetches complete RLS-visible tables in pages and reconciles a full local snapshot. | Load-test with expected clinic volume and concurrency, verify stable pagination/deletions and conflict behavior, implement incremental feeds if needed, and inspect query plans. Sharding is not warranted without measured need. |

Release criteria: every gate must have an owner, written acceptance evidence, a reproducible test or drill where applicable, and sign-off from the clinic's security/privacy and clinical leads. Do not put real patient data into the present FYP backend or device cache to trial these gates. Keep staging and production projects separate, with synthetic staging data.

The encrypted database design must account for **web separately**. The referenced native Drift encryption approach is for Android, iOS and desktop; it does not by itself encrypt browser offline storage. Disable web clinical offline mode or design and audit a separate browser solution before supporting it. Never assume HTTPS encrypts records already saved on a device.

Current checks: 46 Flutter tests pass; analyzer has 48 warnings confined to generated Isar code and no other reported findings. The Android debug APK builds; Android sets `FLAG_SECURE` to suppress screenshots and recent-app previews. The live Supabase security advisor reports three private default-deny tables without policies (expected) and leaked-password protection disabled (open). Android release signing is gated: a trial release task with a non-example ID correctly refused to run without a private keystore. These checks do **not** validate clinical safety, encryption, legal compliance, device behavior, backup recovery, or production operations.
