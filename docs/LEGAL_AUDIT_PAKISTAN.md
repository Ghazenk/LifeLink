US requirements below are assessed because they were requested, not represented as Pakistani law. A Pakistan-based app can still have foreign obligations depending on users and operations.

## Pakistan-specific handoff

1. **Identify operator, province and facility.** Set Admin → Privacy & project settings to the real operator/contact and retention practice. Pakistan is prefilled, but this does not establish an operating licence. For real blood-bank use, consult the relevant provincial blood-transfusion authority and healthcare regulator. Punjab PBTA publishes the 2016 Act and standards; Sindh has its own SBTA. The software cannot substitute for facility licensing, trained staff, donor screening, laboratory validation, consent or traceability requirements.
2. **Children and legal capacity.** The Majority Act describes general majority at 18 with specified exceptions; 13+ registration does not settle capacity or consent. This FYP has no verified parental-consent pathway. Do not use it to onboard children or treat record-sharing “guardianship” as legal guardianship. Obtain a reviewed workflow before pediatric clinical deployment.
3. **Health data and cross-border processing.** Review Mumbai Supabase hosting, optional AI providers, contracts, access, retention, backups, breaches, device encryption and cross-border restrictions with the operator's counsel/security lead. Only synthetic data is appropriate until those decisions are made. No migration of real records or production certification was performed.
4. **Current laws versus drafts.** PECA addresses unauthorized access/copying and other misuse; access controls are relevant safeguards, not proof of complete statutory compliance. MoITT publishes Personal Data Protection **Bill** drafts. A draft is not evidence of an enacted Act. This audit did not verify an enacted comprehensive personal-data statute from the official sources consulted; confirm the latest Gazette/current law and sectoral obligations before release. Do not advertise “PDPA compliant”.
5. **Copyright and clinical claims.** Use Pakistan's copyright framework for the local notice process. Verify asset ownership and do not promise that AI text is accurate, exclusive or cleared. Warnings do not authorize medical practice or remove liability for unsafe design.
6. **Operational checks beyond this patch.** Supabase advisor still flags leaked-password protection disabled; enable it if available for the plan. Review database maintenance updates, staff access, recovery emails/SMTP, backup restoration and incident handling. These cannot be solved by policy wording alone.

### Conditional US DMCA agent registration (original checklist)

If counsel determines US Section 512 protection is relevant: use [Copyright Office DMCA Directory](https://www.copyright.gov/dmca-directory/), create a registration account, add the service provider's legal name and physical address plus alternate app/business/domain names users could search, enter the designated agent's name/address/phone/email, pay the current **$6** designation fee and submit. Publish the same details through Admin → Privacy & project settings → Copyright contact fields. Keep them current and renew within **three years** (amending/resubmitting restarts the period). Record the registration confirmation and renewal deadline. Agent designation alone does not establish safe harbor; legal counsel should evaluate scope, notice handling and repeat-infringer requirements. Do not force the US counter-notice court-consent procedure on Pakistani users by default.

## Verification evidence

- SQL `supabase/tests/legal_safeguards.sql`: live transaction/rollback verified missing/false/null/string/numeric age values and missing Terms rejected; zero retained users/profiles/identities for those attempts; trusted staff source cannot bypass age; user metadata cannot forge trusted source; eligible public/staff inserts succeed without role escalation.
- SQL `supabase/tests/security_and_sync.sql`: existing authorization/clinical atomicity tests rerun after new trigger, using updated eligible fixtures; passed and rolled back.
- Live Auth REST bypass probes: false and string age declarations rejected with SQLSTATE 23514 (Supabase presents trigger rejection as HTTP 500); zero test accounts retained. This is an intentional registration rejection and does not alter existing login. UI validates eligibility before sending a valid signup.
- Live schema inspection: registration BEFORE trigger enabled; settings RLS enabled; public read/admin-only update policies retained; Pakistan default applied; zero Storage buckets.
- `manage-users` deployed version 2, ACTIVE, JWT verification enabled. Shared strict age validation unit test passed alongside four AI/http validation tests; both functions pass Deno type checks.
- Static scans of runtime `lib`, `web`, `supabase/functions` and manifests: no analytics imports, remote font/CDN URL, payments/marketing SDK imports, runtime console logging, private-key literals, OAuth/invite calls or file-Storage upload calls. OTP calls are limited to transactional signup verification and password recovery. Negative findings are limited to this repository and inspected live schema, not external dashboards, host settings or all history.
- Flutter age/Terms/copyright tests added; responsive tests updated for the age gate. 29 Flutter tests passed; 5 Deno tests passed; Windows and Android debug builds succeeded. The Android file_picker compile SDK mismatch was fixed in `android/build.gradle.kts`. Analyzer has zero errors and 48 pre-existing generated Isar experimental-API warnings. Device behavior, Apple builds and production signing are not verified. Details are recorded in `SECURITY_AND_SETUP.md`.
